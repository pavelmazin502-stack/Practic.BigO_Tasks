# Архитектура проекта

## Структура кода

* `src/ds/` — свои структуры данных (`DynamicArray`, `HashTable`, `BinaryHeap`).
* `src/core/` — структура задачи (`task.hpp`) и логика управления (`task_manager.hpp`).
* `src/storage/` — чтение и запись файла (`file_storage.hpp`).
* `src/cli/` и `src/main.cpp` — разбор команд из консоли и вывод результата.

## Модель задания

Каждая задача (`Task`) хранит 8 полей:
* `id` — уникальный идентификатор (задаётся вручную или генерируется как `task-1`, `task-2`, ...).
* `type` — тип задачи.
* `payload` — текст с данными задачи.
* `priority` — приоритет от `0` до `100` (чем больше число, тем раньше запустится).
* `status` — текущее состояние.
* `created_at` — время создания (Unix timestamp).
* `updated_at` — время последнего изменения.
* `error` — текст ошибки (если задача завершилась с ошибкой).

## Переходы состояний

Всего 5 статусов: `queued`, `running`, `completed`, `failed`, `cancelled`.

```text
               ┌──► completed
queued ──► running
   │           └──► failed
   └──► cancelled
```

Разрешённые переходы:
* `queued` → `running` (`start-next`)
* `queued` → `cancelled` (`cancel`)
* `running` → `completed` (`complete`)
* `running` → `failed` (`fail`)

Из `completed`, `failed` и `cancelled` переходить никуда нельзя. При попытке сделать запрещённый переход выкидывается ошибка, состояние и файл не меняются.

## Взаимодействие структур данных

Внутри `TaskManager` работают три структуры:
1. `DynamicArray<Task> tasks` — хранит сами задачи. Новые добавляются только в конец, ничего не удаляется, поэтому индексы задач не меняются, а `list` всегда идёт в порядке создания.
2. `HashTable<string, size_t> id_to_index` — связывает строковый `id` с индексом задачи в массиве `tasks`, чтобы находить любую задачу за `O(1)`.
3. `BinaryHeap<QueueItem> ready_queue` — бинарная куча для выбора следующей задачи. Хранит не всю задачу целиком, а только `{priority, index}`. Сначала сравнивается `priority` (больше — лучше), а если приоритеты равны — меньший `index` (кто создан раньше, тот и запускается первым).

## Разрешение коллизий и хеш-функция

* **Хеш-функция:** используется полиномиальный хеш с основанием `31`. Цикл проходит по всем символам ключа и считает `hash = hash * 31 + static_cast<unsigned char>(key[i])` в 64-битном беззнаковом типе `uint64_t`, после чего индекс корзины вычисляется через остаток от деления `hash % capacity`..
* **Коллизии:** используется **метод цепочек**. В каждой ячейке массива `buckets` лежит указатель на односвязный список узлов `Node`. Если два ключа попали в одну ячейку, новый узел просто добавляется в начало её списка. Если ключ уже есть в списке — его значение обновляется.

## Изменение размера

* **В `HashTable`:** перед вставкой проверяется заполненность. Когда она достигает **75%** (`(size + 1) * 4 >= capacity * 3`), вызывается `rehash()`: размер массива корзин умножается на 2, а все существующие узлы перевешиваются в новые ячейки без пересоздания самих узлов.
* **В `DynamicArray`:** когда место заканчивается, выделяется новый массив в 2 раза больше и элементы копируются туда.

## Согласованность очереди и индекса

Если задачу отменили (`cancel`), её статус сразу меняется на `cancelled` в массиве `tasks` по индексу из хеш-таблицы. Из середины кучи `ready_queue` она при этом не удаляется, чтобы не искать её там за `O(n)`.

Вместо этого используется **ленивый пропуск**: когда вызывается `start-next`, он достаёт верхний элемент кучи и проверяет актуальный статус задачи в `tasks[index]`. Если задача уже не в статусе `queued`, она просто отбрасывается, и берётся следующий элемент из кучи. Так отменённая задача никогда не запустится.

## Формат хранения

Данные сохраняются в текстовый TSV-файл (колонки разделены табуляцией `\t`):
* 1-я строка — версия формата: `TASKCTL_VERSION=1`.
* Остальные строки — по одной задаче на строку, ровно 8 колонок: `id`, `type`, `priority`, `payload`, `status`, `error`, `created_at`, `updated_at`.
* Переносы строк, табы и слэши внутри текста (`\n`, `\r`, `\t`, `\`) экранируются при записи и восстанавливаются при чтении.
* **Надёжная запись:** сначала всё пишется во временный файл `<имя>.tmp`, и только после успешной записи он переименовывается поверх основного файла. Если программа упадёт в процессе, старые данные не испортятся.
* **Проверка файла:** при загрузке всё сначала читается во временный объект. Если файл пустой, версия неверная, колонок не 8 или есть битые значения — выдаётся ошибка, а сам файл не перезаписывается.
